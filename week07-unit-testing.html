Idea 1 · Why we test

Two questions every test answersสองคำถามที่ทุกเทสต์ต้องตอบ

Verification

Did we build it right?เราสร้างมันถูกวิธีไหม?

Does the code match the spec, with no bugs and correct logic? Caught by unit tests & reviews.

โค้ดตรงกับ spec ไหม ไม่มีบั๊ก ตรรกะถูกต้อง? ตรวจจับได้ด้วย unit test และการรีวิวโค้ด

Validation

Did we build the right thing?เราสร้างสิ่งที่ถูกต้องไหม?

Is this what the user actually needed? Caught by demos, acceptance tests, feedback.

นี่คือสิ่งที่ผู้ใช้ต้องการจริงหรือเปล่า? ตรวจจับได้ด้วยการเดโม acceptance test และ feedback

In plain terms · พูดง่าย ๆ

A reminder that fires on the wrong day still "runs". It passes a glance but fails verification. A perfectly-coded feature nobody asked for passes verification but fails validation. You need both.

การแจ้งเตือนที่เด้งขึ้นผิดวันก็ยัง "รันได้" ดูผ่าน ๆ เหมือนใช้ได้ แต่ไม่ผ่าน verification ส่วนฟีเจอร์ที่เขียนโค้ดได้สมบูรณ์แบบแต่ไม่มีใครต้องการ จะผ่าน verification แต่ไม่ผ่าน validation ต้องมีทั้งสองอย่าง

In plain terms · พูดง่าย ๆ

It's writing (left arm) and proofreading (right arm). You proofread each part against what you meant to write: verification = "no typos, matches the plan"; validation = "this is the chapter the reader actually needed."

เหมือนการเขียน (แขนซ้าย) กับการพิสูจน์อักษร (แขนขวา) เราตรวจแต่ละส่วนเทียบกับสิ่งที่ตั้งใจเขียน verification = "ไม่มีคำผิด ตรงตามแผน" ส่วน validation = "นี่คือบทที่ผู้อ่านต้องการจริง ๆ"

Idea 2 · What a test actually is

Give known input → check the result equals what you expectใส่ input ที่รู้ค่า → ตรวจว่าผลลัพธ์ตรงกับที่คาดไว้

If the real output matches the expected output, the test passes. If not, it fails, and you just found a bug cheaply, before a user did.

ถ้าผลลัพธ์จริงตรงกับที่คาดไว้ เทสต์จะผ่าน (pass) ถ้าไม่ตรง เทสต์จะล้มเหลว (fail) แปลว่าเราเพิ่งเจอบั๊กได้แบบต้นทุนต่ำ ก่อนผู้ใช้จะเจอ

In plain terms · พูดง่าย ๆ

Type 2 + 2 into a calculator and you expect 4. If the screen shows 5, the calculator has a bug. A test is exactly that check: an expected answer you write down once, so the computer re-checks it for you every time.

กด 2 + 2 ในเครื่องคิดเลข เราคาดหวังว่าจะได้ 4 ถ้าหน้าจอขึ้น 5 แปลว่าเครื่องคิดเลขมีบั๊ก เทสต์ก็คือการตรวจแบบนั้นเป๊ะ ๆ เราเขียนคำตอบที่คาดหวังไว้ครั้งเดียว แล้วคอมพิวเตอร์จะตรวจซ้ำให้ทุกครั้ง

Idea 3 · The smallest useful test

A unit test checks one small piece in isolationUnit test ตรวจชิ้นส่วนเล็ก ๆ หนึ่งชิ้นแบบแยกเดี่ยว

Usually one functionปกติคือฟังก์ชันเดียว

ทดสอบ tasks_due_for_reminder() ตัวเดียว ไม่มีฐานข้อมูล ไม่มี UI ไม่มีเน็ตเวิร์ก

จึงรันได้ตลอดเวลาหลังแก้โค้ดทุกครั้ง ไม่ใช่รันครั้งเดียวตอนท้าย

Precise

Pinpoints the breakชี้จุดที่พังได้ตรง ๆ

When one fails, you know exactly which piece broke. No hunting.

เมื่อเทสต์ตัวไหน fail เราจะรู้ทันทีว่าชิ้นไหนพัง ไม่ต้องไล่หา

In plain terms · พูดง่าย ๆ

Unit tests are like checking each LEGO brick is the right shape before you build the castle. Cheaper to catch a bad brick now than to tear down the whole thing later.

Unit test เหมือนการเช็กว่าตัวต่อ LEGO แต่ละชิ้นมีรูปทรงถูกต้องก่อนต่อเป็นปราสาท จับชิ้นที่เสียตอนนี้ถูกกว่ารื้อทั้งปราสาททีหลัง

def test_reminds_open_task_1_day_before():
    tasks = [Task(due=date(2026,8,10), status='open')]
    assert tasks_due_for_reminder(tasks, date(2026,8,9)) == tasks

def test_does_not_remind_done_task():
    tasks = [Task(due=date(2026,8,10), status='done')]
    assert tasks_due_for_reminder(tasks, date(2026,8,9)) == []

Choosing test inputs · two classic techniques (SWEBOK · Sommerville §8)

You can't test every input, so test the right fewทดสอบทุก input ไม่ได้ จึงต้องเลือกทดสอบเฉพาะตัวที่ใช่

Equivalence partitioning (EP)

Group inputs that behave the sameจัดกลุ่ม input ที่ทำงานเหมือนกัน

Split inputs into classes the code treats alike, then test one value from each: one valid, one too short, one too long. One test now stands for a whole range.

แบ่ง input เป็นกลุ่ม (class) ที่โค้ดจัดการแบบเดียวกัน แล้วทดสอบค่าเดียวจากแต่ละกลุ่ม เช่น ค่าที่ถูกต้อง 1 ค่า สั้นเกิน 1 ค่า ยาวเกิน 1 ค่า เทสต์เดียวจึงแทนค่าทั้งช่วงได้

Boundary value analysis (BVA)

Bugs hide at the edgesบั๊กชอบซ่อนอยู่ที่ขอบ

Test right at and around each boundary: the first and last allowed value, and just outside. This is where "≤ vs <" and off-by-one bugs live.

ทดสอบที่ขอบและรอบ ๆ ขอบ คือค่าแรกและค่าสุดท้ายที่ยอมรับได้ และค่าที่เลยขอบไปนิดเดียว ตรงนี้คือที่อยู่ของบั๊ก "≤ กับ <" และ off-by-one

StudyMate: a task title must be 1–100 chars. EP picks one per band (0 · 50 · 101); BVA adds the edges (1 · 100)StudyMate: ชื่องานต้องยาว 1–100 ตัวอักษร EP เลือกค่าละหนึ่งตัวต่อช่วง (0 · 50 · 101) BVA เพิ่มค่าที่ขอบ (1 · 100)

Five well-chosen tests beat a hundred random ones. Same idea for a due date (past / today / future) or a reminder window. Source: Sommerville 9e §8.1.2; SWEBOK v4 Testing KA.

เทสต์ 5 ตัวที่เลือกมาดี ชนะเทสต์สุ่ม 100 ตัว ใช้แนวคิดเดียวกันได้กับวันครบกำหนด (อดีต / วันนี้ / อนาคต) หรือช่วงเวลาแจ้งเตือน

    Write task scenariosเขียนสถานการณ์งาน

Depend on today's date / the networkพึ่งวันที่ปัจจุบัน / เน็ตเวิร์ก

A test that passes Monday and fails Tuesday isn't a test. It's a coin flip.

เทสต์ที่ผ่านวันจันทร์แต่ fail วันอังคาร ไม่ใช่เทสต์ แต่เป็นการโยนเหรียญ

In plain terms · พูดง่าย ๆ

A good test is like a good exam question: it asks about one thing, and a wrong answer tells you exactly what the student (here, your code) got wrong.

เทสต์ที่ดีเหมือนข้อสอบที่ดี ถามเรื่องเดียว และถ้าตอบผิดก็บอกได้ทันทีว่านักเรียน (ในที่นี้คือโค้ด) ผิดตรงไหน

The rule · กฎ

Ask AI for the code and the tests, then check the tests cover your acceptance criteria. It almost always leaves one out. Finding that gap is the engineering, and it's what you're graded on.

ให้ AI เขียนทั้งโค้ดและเทสต์ แล้วตรวจว่าเทสต์ครอบคลุม acceptance criteria ครบ AI แทบจะลืมไปหนึ่งข้อเสมอ การหาช่องโหว่นั้นเจอคืองานวิศวกรรม และคือสิ่งที่ใช้ให้คะแนน

Case study · When a reused unit went untested

Ariane 5, Flight 501: a 37-second, ~$370M bugAriane 5 เที่ยวบิน 501: บั๊ก 37 วินาที มูลค่า ~370 ล้านดอลลาร์

What happened · เกิดอะไรขึ้น

Reused code, new rocketโค้ดเดิม จรวดใหม่

Inertial-reference software was reused from Ariane 4. Ariane 5 flew faster, so a horizontal-velocity value overflowed when a 64-bit number was converted into a 16-bit one. The unhandled error shut down both the primary and backup units; the rocket veered and self-destructed 37 s after liftoff.

ซอฟต์แวร์ระบบนำร่องเฉื่อยนำกลับมาใช้จาก Ariane 4 แต่ Ariane 5 บินเร็วกว่า ค่าความเร็วแนวนอนจึงล้น (overflow) ตอนแปลงตัวเลข 64 บิตเป็น 16 บิต error ที่ไม่ได้จัดการทำให้ทั้งเครื่องหลักและเครื่องสำรองดับ จรวดเสียทิศทางและทำลายตัวเอง 37 วินาทีหลังปล่อย

Why a test would have caught it · ทำไมเทสต์จะจับได้

The new range was never testedไม่เคยทดสอบกับช่วงค่าใหม่

The conversion was never tested with Ariane 5's larger velocity values. The reused path had no test for the new operating range, and the code assumed the value could not overflow.

การแปลงค่านี้ไม่เคยถูกทดสอบกับความเร็วที่สูงขึ้นของ Ariane 5 โค้ดที่นำกลับมาใช้ไม่มีเทสต์สำหรับช่วงการทำงานใหม่ และโค้ดสันนิษฐานว่าค่าจะไม่มีทางล้น

The lesson · บทเรียน

Reused code is not tested code. Re-test every reused component against the new context's inputs and boundaries: exactly the edge cases that AI-generated code also skips.

โค้ดที่นำกลับมาใช้ ไม่ใช่โค้ดที่ผ่านการทดสอบแล้ว ต้องทดสอบทุกส่วนที่นำกลับมาใช้ซ้ำกับ input และขอบเขตของบริบทใหม่ ซึ่งเป็น edge case แบบเดียวกับที่โค้ดจาก AI มักข้ามไป

Source: ESA/CNES Ariane 501 Inquiry Board Report (Lions et al., 1996).

AI Critique #7 · last 10 min · on A4

Spot it · explain it · fix itหาจุดผิด · อธิบาย · แก้ไข

"I added a test so you're covered: assert add_task('Buy milk') is not None. Green across the board, ship it." an AI coding assistant, confidently
1 · Spot

What's weak?อะไรอ่อนแอ?

The test only checks "something came back." It never checks the task was stored correctly, with the right title or due date.

เทสต์ตรวจแค่ว่า "มีอะไรคืนกลับมา" ไม่เคยตรวจว่างานถูกบันทึกถูกต้อง มีชื่อหรือวันครบกำหนดที่ถูก

2 · Explain

Why is it wrong?ทำไมถึงผิด?

A test that can't fail for the real bug gives false confidence. "Not None" passes even if the data is garbage.

เทสต์ที่ไม่มีทาง fail กับบั๊กจริงทำให้มั่นใจแบบผิด ๆ "Not None" ผ่านได้แม้ข้อมูลจะเป็นขยะ

3 · Fix

The right wayวิธีที่ถูก

Assert on the result: the stored task's title equals 'Buy milk', status is open, and an invalid input is rejected.

assert ที่ผลลัพธ์: ชื่องานที่บันทึกต้องเท่ากับ 'Buy milk' สถานะเป็น open และ input ที่ผิดต้องถูกปฏิเสธ

# a stronger version · เวอร์ชันที่ดีกว่า
def test_add_task_stores_title_and_open_status():
    task = add_task('Buy milk')
    assert task.title == 'Buy milk'
    assert task.status == 'open'

def test_add_task_rejects_empty_title():
    with pytest.raises(ValueError):
        add_task('   ')
