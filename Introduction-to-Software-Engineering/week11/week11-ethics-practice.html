intro2se-ch10-ethics-practice.fig / SE ethics
IDEA 1: DUTIES BEYOND “IT COMPILES”

Professional codes spell out what we owe

Public interest

People come first

Act consistently with public health, safety and welfare, above your own or your client's convenience.

Honesty

Be truthful

Don't overstate what the software does, hide known defects, or take credit for others' work.

Competence & care

Do work you can stand behind

Only sign off on work you believe is right, and keep learning. The ACM/IEEE Code is the shared standard.

In plain terms

A profession is a promise. Doctors, engineers and now software builders hold power over people's lives. The code of ethics is how we keep that trust.

intro2se-ch10-ethics-practice.fig / Where the Code comes from
IDEA 1a: WHY SOFTWARE ENGINEERING NEEDED ITS OWN CODE

Two societies, one code for a new profession

1993
IEEE-CS steering committee; ACM commission
→
1994
Joint ACM + IEEE-CS committee
→
1997
Draft in Comm. ACM, for comments
→
1999
Version 5.2 approved
The goal

Make SE a profession

The joint committee set out to define standard terms, a body of knowledge, curricula and ethical standards for software engineers.

What a code does

Educate, inspire, inform

It tells members what peers expect, tells the public what the profession is responsible for, and gives practical advice. It is not a law.

Who it covers

Including students

Practitioners, educators, managers, policy makers, trainees and students of the profession. That means you, now.

The preamble, in one line

People who build software have real chances “to do good and to cause harm”, and to enable others to do either. The code exists so that power is used for good.

Source: Gotterbarn, Miller & Rogerson, “Software Engineering Code of Ethics,” Comm. ACM 40(11), Nov 1997 (draft for comment). Final version 5.2 approved 1999.

intro2se-ch10-ethics-practice.fig / Three levels of obligation
IDEA 1c: HOW THE CODE IS BUILT

Every principle works at three levels

Level 1: Aspire

To be human

Values every person shares, such as honesty and fairness. They set a direction and need your own ethical judgment.

Level 2: Expect

To be professional

Duties every professional owes, because people affected by your work deserve special care.

Level 3: Demand

To use good practices

Specific, often measurable behaviours of software engineering today, close to the current state of the art.

LevelExample for “Public” (our illustration of the idea)
AspireBe fair and truthful in everything you say about the software.
ExpectAccept full responsibility for your own work, including the parts AI drafted.
DemandApprove software only if you have good grounds to believe it is safe, meets its specification and has passed appropriate tests.

Source: Gotterbarn, Miller & Rogerson (1997), preamble. The code does not label each clause with a level; the table shows how the idea applies.

intro2se-ch10-ethics-practice.fig / When principles conflict
IDEA 1f: USING THE CODE WHEN IT GETS HARD

The code is not an algorithm: five questions to ask

1

Who is affected?

Think broadly: users, third parties, people who never touch the app.

2

Are we treating people with respect?

You and your colleagues, towards every person involved.

3

How would a well-informed public see it?

If they knew all the facts, would they accept your decision?

4

What happens to the least empowered?

The people with the least power to complain or protect themselves.

5

Would an ideal professional do this?

Would respected, experienced peers who knew the facts judge it worthy?

Try it

Ship Friday, or fix the leak?

Affected: every user whose data can leak. Least empowered: users who never chose this app. Informed public: would not accept “we knew, but the deadline came first.” Answer: report the risk and delay or fix (Principle 1).

Why five questions, not a rulebook

Principles can conflict with each other or with other rules. The code gives no automatic answer; it gives you a way to judge, and a written standard the whole team can point to when they say no.

Source: Gotterbarn, Miller & Rogerson (1997), preamble. Not exhaustive: the code warns against using any single clause in isolation to justify a mistake.

intro2se-ch10-ethics-practice.fig / Four everyday issues
IDEA 1g: WHERE ETHICS SHOWS UP (SOMMERVILLE §1.2)

Four issues you'll meet in ordinary work

#1

Confidentiality

Respect your employer's and client's information, with or without a signed agreement.

#2

Competence

Don't misrepresent your skill, and don't take on work beyond it.

#3

IP rights

Know and respect patents, copyright and licences. Protect what isn't yours.

#4

Computer misuse

Don't use your skills to harm others' systems, from time-wasting to malware.

Connects to this course

Confidentiality + IP = why you never commit secrets or copy code without a licence. Competence + misuse = why “the AI wrote it” never excuses harm.

Source: Sommerville 9e, §1.2 Software engineering ethics.

intro2se-ch10-ethics-practice.fig / Data ethics & privacy
IDEA 2: CAN vs SHOULD

Just because you can collect it doesn't mean you should

Minimise

Collect the least

Only what the feature truly needs. Every extra field is a liability you now have to protect.

Protect

Guard what you hold

Secure it, limit who can see it, and honour people's right to see, correct and delete (PDPA, Ch8).

Be transparent

Say what and why

Tell people what you collect and how it's used, in plain language, before they hand it over.

Carries Ch8 forward

Security was the how; data ethics is the whether. The most private data is the data you chose never to collect. Which fields in your prototype are not really needed?

intro2se-ch10-ethics-practice.fig / Responsible AI use
IDEA 3: AI-FIRST, BUT A PERSON IS ACCOUNTABLE

AI can be wrong or biased, and it cannot be responsible

DO

Keep a human sign-off

A person reads, tests and approves. Accountability can't be delegated to a model.

Be transparent

Disclose where AI was used. That is exactly what your AI-Use Statement is for.

Watch for bias and error

AI reflects its training data. Check outputs against reality, especially about people.

DON'T

“The AI said so”

Not a defence. If you shipped it, you own it, bug and bias included.

Paste private data into prompts

Treat a prompt as public. Never feed real personal data or secrets.

Pass AI work off as fully your own

Honesty (Idea 1) applies to how the work was made, too.

In plain terms

AI is like a very fast intern: brilliant first drafts, but you sign the work before it goes out. If it's wrong, the boss (you) answers for it, never the intern. This is one of the four oral-exam criteria.

intro2se-ch10-ethics-practice.fig / Backdoor in your own code
CONCEPT: BACKDOOR IN CODE

A backdoor can also arrive in code AI writes for you

Example: login function

if password == "dev-2569": return True

Nobody asked for this line, yet all login tests still pass. Anyone who knows the value gets in without a real password.

Why tests miss it

Tests check what should work

They rarely check for an extra way in. That is why you read the code before committing, and why review still matters.

What to do

Remove the line, tell the team, and test the login again. Bug or backdoor, intended or not, the risk is the same, and the team that ships it owns it.

intro2se-ch10-ethics-practice.fig / Case study: local models
CASE STUDY: WHAT ABOUT A LOCAL MODEL?

“Local” does not mean “trusted”

RouteHow it worksCan it send data out?
Hidden code in the filePickle files or trust_remote_code can run code when loaded.Yes, like ordinary malware. No trigger needed.
Backdoor in the weightsTraining makes the model change its output on a trigger.Not alone. Weights are numbers; they need software around them.
Model + tools or UIA triggered output calls a tool, or puts data in a link or image URL.Yes, if the tool has permission or the UI loads the URL.
Reduce the risk

Check the publisher and hash; prefer safetensors; avoid trust_remote_code; use a sandbox with no network; give tools the least privilege; a person confirms risky actions.

The limit

A file scan finds hidden code, not behaviour learned in training. Design so that even a triggered model cannot get data out.

intro2se-ch10-ethics-practice.fig / Professional practice
IDEA 4: HABITS THAT MATTER AS MUCH AS CODE

Being easy to work with is an engineering skill

Communicate

Clearly and early

Say what you're doing, and say when you're stuck, before the deadline.

Commit

Keep your word

Deliver what you said, or renegotiate early. Reliability is reputation.

Feedback

Give and take it

Critique the work, not the person; receive it without defensiveness.

Document

Leave a trail

A README and clear commits so others, and future-you, can follow.

Why it's graded

These are the habits the oral exam and the GitHub contribution factor reward: the parts of engineering that no model does for you.

Practice like the real exam

1.In the ACM/IEEE-CS Software Engineering Code of Ethics, which principle comes first?

  1. A.Client and employer.
  2. B.Product.
  3. C.Public.
  4. D.Self.

2.A study-reminder prototype asks every user for their national ID number. Which data-ethics principle does this break most directly?

  1. A.Transparency.
  2. B.Data minimisation.
  3. C.Competence.
  4. D.Intellectual property.

3.A bug in AI-generated code exposes users' data after release. Who is accountable?

  1. A.The company that trained the AI model.
  2. B.No one, because the code was generated automatically.
  3. C.The engineers who reviewed and shipped the code.
  4. D.The user who reported the bug.

4.What does Continuous Integration (CI) do?

  1. A.It writes the unit tests for you.
  2. B.It runs the tests automatically on every push.
  3. C.It deploys the system once, at the end of the project.
  4. D.It replaces code review.
